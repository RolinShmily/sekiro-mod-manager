# 04. 核心工程决策与选型权衡清单

> 本文档整理出在进入工程代码编写前，需要研发团队与产品负责人明确回答的 5 项核心决策问题。每项问题均包含背景动因、候选方案详细对比、利弊分析以及推荐基准路线。

---

## 决策概览矩阵

| 决策编号 | 决策议题 | 推荐方案 (Default) | 备选方案 | 核心权衡维度 |
| :---: | :--- | :--- | :--- | :--- |
| **Q1** | **应用宿主技术栈选型** | **Tauri v2 + Rust + Vue 3/TS** | Electron / Python PyQt / CLI (Go) | 内存占用、打包体积、Win32 API 调用便利度 |

## 决策 1：应用宿主技术栈选型

### 1.1 背景与考量点
只狼 Mod 管理器重度依赖 Windows 文件系统底层调用（`CreateHardLinkW`, 盘符卷标检测, 路径大小写归一化），同时需要流畅的拖拽（Drag-and-Drop）与直观的列表重排。我们需要在“系统级 API 操控能力”、“安装包体积极致度”与“现代化 UI 构建效率”之间取得平衡。

### 1.2 方案对比

| 方案 | 架构 | 打包体积 | 运行时内存 | Win32 底层控制 | 开发与生态体验 |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **方案 A (推荐)<br>Tauri v2 + Rust** | Rust 底层 + Web 前端 (WebView2) | ~8-15 MB | ~30-50 MB | **极强**<br>直接调用 `windows-sys` 或 `winapi`，无缝支持硬链接与卷检测。 | 前端自由度极高，代码性能极强；Rust 学习曲线稍陡，但对文件操作极度安全。 |
| **方案 B<br>Electron + Node.js** | Chromium + Node.js 运行时 | ~80-120 MB | ~150-250 MB | **中等**<br>需引入原生 C++ 扩展 (Node-API) 或依赖 `fs.link`。 | Web 生态最繁荣，开发极其迅速；但对于极简专属工具而言包体偏大、内存偏重。 |
| **方案 C<br>Python + PyQt6 / PySide6** | Python 解释器 + Qt 原生控件 | ~40-60 MB (打包后) | ~60-100 MB | **良好**<br>可通过 `ctypes` 或 `win32file` 驱动 API。 | 研发速度快，原型验证极速；但 Windows 下多线程与打包（PyInstaller/Nuitka）常有环境踩坑。 |
| **方案 D<br>纯 CLI / TUI (Rust 或 Go)** | 终端字符界面 (Ratatui / Bubbletea) | ~3-8 MB | ~10-20 MB | **极强** | 体积最小，极客属性强；但对普通游戏小白门槛较高，拖拽压缩包体验受限。 |

### 1.3 推荐结论与建议立场
- **立论**：推荐 **Tauri v2 + Rust + Vue 3 / Tailwind CSS**。
- **原因**：Tauri 打包后仅十余兆，内存占用仅为 Electron 的 1/5，利用 Windows 10/11 自带的 WebView2，界面美观现代；后端 Rust 负责密集的文件哈希、解压、NTFS 硬链接操作具有零开销抽象与内存安全优势。

## 决策 2：UI 交互形态与视觉风格

### 2.1 候选方案
- **形态 A：标准中型双栏窗体 (Recommended)**  
  左栏为 Mod 清单与启停开关（支持拖拽上下滑动排序），右栏为选中 Mod 的详情面板（包含文件结构树、冲突报告高亮、作者元数据），顶部为常驻的“环境自检指示灯”、“一键部署”与“清空还原”按钮。
- **形态 B：极简紧凑小窗 (Compact Card)**  
  仅一个长条形卡片界面，只有列表和部署按钮，冲突等详情折叠在弹窗中。
- **形态 C：终端交互 (TUI 模式)**  
  在终端中利用键盘快捷键 `[Space]` 切换状态，`[J]/[K]` 调整顺序，`[D]` 执行部署。

### 2.2 推荐结论与建议立场
- **推荐形态 A**。只狼 Mod 的核心痛点是“冲突”，右侧固定的详情/冲突透视栏能让玩家立即看懂为什么某个 Mod 会覆盖另一个 Mod（例如 `parts/wp_a_0300.partsbnd.dcx` 被上方高优先级 Mod 截获），透明度最高。

## 3. 决策 3：压缩包解压与归一化引擎实现方式

### 3.1 背景与考量点
只狼 Mod 压缩包通常采用 `.zip`、`.7z`，偶见 `.rar`。归一化需要快速遍历压缩包内部文件清单，判断锚点目录后解压到 Staging。

### 3.2 候选方案
- **方案 A：内置原生解析库 (In-process Native)**  
  Rust 下采用 `zip` + `sevenz-rust`，无外部可执行依赖，解压流由代码完全控制，跨平台封装好。但对罕见的不规范 rar 支持需要额外处理。
- **方案 B：外挂携带 `7z.exe` / `7z.dll` (Out-of-process Standalone)**  
  管理器发布包内附带官方精简版 `7za.exe` 或 `7z.dll`，后端直接调用子进程执行解压。
  - *优势*：无敌的压缩格式兼容性（完美处理所有 zip, 7z, rar, 分卷包，容错各种损坏编码）。
  - *劣势*：需要管理外部进程状态与临时输出解析。

### 3.3 推荐结论与建议立场
- **Phase 1 MVP 推荐方案 B（携带精简版 7za.exe）或方案 A 中的 zip/7z 双核心**。对于 Windows 游戏 Mod 而言，社区压缩包五花八门，`7z` 进程调用的容错率和解压速度被历代管理器证明最为稳健。

## 4. 决策 4：核心参数冲突 (`gameparam.parambnd.dcx`) 处理策略深度

### 4.1 背景与考量点
只狼没有《艾尔登法环》那样的 regulation.bin 独立合并工具，其参数全打包在 `gameparam.parambnd.dcx` 内部。两个玩法 Mod 同时改动此文件，硬链接只能保留一个。

### 4.2 候选方案
- **策略 A：仅高危可视化警报与遮蔽提示 (Recommended for MVP)**  
  不改动文件，只在冲突视窗中用醒目红色叹号警告：“当前有 N 个 Mod 争夺参数表，Mod [A] 胜出，Mod [B] 的平衡性数值将完全失效！”允许用户调整优先级决定谁生效。
- **策略 B：阻断部署 (Strict Guard)**  
  一旦检测到多个 Mod 包含该文件，禁止执行一键部署，强制用户只能勾选其中一个。
- **策略 C：内置 WitchyBND 联动全自动合并 (Auto Merge)**  
  尝试调用 WitchyBND 解包两个 dcx 为 xml，比对 param 表逐行合并再重封。

### 4.3 推荐结论与建议立场
- **坚决选择策略 A（Phase 3 补充半自动辅助）**。
- **原因**：自动化合并 FromSoft 参数是著名的“黑盒天坑”。参数表之间存在大量外键依赖与 SpEffect 级联。错误的自动合并会导致游戏开局读条 100% 崩溃甚至坏档。管理器应清晰履行“诚实告知覆盖关系”的职责，绝不在未掌握语义时做盲目二进制定制合并。

---

## 5. 决策 5：暂存库 (Staging) 存储位置与跨盘应对

### 5.1 背景与考量点
NTFS 硬链接无法跨盘符（跨 Volume）。若游戏在 `D:\` 盘，暂存库若默认在 `C:\Users\...\AppData`，硬链接将全部失效。

### 5.2 候选方案
- **策略 A：同盘就近引导 (Smart Proximity Prompt - Recommended)**  
  在首次启动定位 `sekiro.exe` 后，检测其所在盘符（如 `D:`），默认推荐在 `D:\SekiroModManager_Staging\` 或 `sekiro.exe` 同级上一层建立暂存库。若用户自行更改至异盘，弹出醒目说明：“跨盘将失去硬链接秒级部署能力，转为耗费磁盘空间的物理拷贝，是否继续？”
- **策略 B：隐藏细节，无脑降级为全量复制**  
  将暂存库固定死在系统 AppData，每次部署直接在 `mods/` 下执行完整物理文件复制。
  - *代价*：失去秒级部署，每次部署耗费大量磁盘写入寿命与等待时间，违背极简高效原则。

### 5.3 推荐结论与建议立场
- **立论**：选择 **策略 A**。通过友好的向导引导同盘存放，将 NTFS 硬链接的技术红利发挥到极致。
